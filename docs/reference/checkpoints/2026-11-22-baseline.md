# November 22 checkpoint: what survives a worker restart?

The first engine change keeps a named fan-out item reusable across editions while allowing its value to change. Four smaller experiments establish where this feature stops helping. They use the public CLI, two real vendor reads, a local transactional sink, and an existing cloud workflow run. Each experiment asks what a new process can know before doing work again.

## Reusing computation after an input changes

In the baseline commit `0f57d46`, a file manifest contained two objects. A worker calculated a value from each object. A dependent node recorded the joined results. Changing the estimate for `US-2022` from 333287557 to 333271411 preserved the row's identity. Bare resume completed successfully, skipped four completed nodes, and retained the old estimate. These are two Census vintages for the same year. The problem also applies to a revised quote line, CRM record or study extraction. [2022 Census release](https://www.census.gov/newsroom/press-kits/2022/2022-national-state-population-estimates.html), [2023 Census release](https://www.census.gov/newsroom/press-kits/2023/national-state-population-estimates.html)

A new `sqrlly run workflow.yaml --refresh-items` invocation compares top-level manifest values with the values behind the checkpointed outputs. An ordinary `--resume` keeps its fault-recovery meaning, including the ability to avoid repeating a completed external action. For a manifest generated by an upstream command, `--refresh-items --resume-from <producer>` gives that command a chance to read changed source data. An item containing a file path or a remote ID still needs an explicit revision or content hash to represent a change behind that reference. [Public contract](../../../SCHEMA.md#repeating-a-node)

The [benchmark](../../../tools/bench-manifest-refresh.py) executes the installed CLI for every measurement, records each worker process invocation, and checks the entire ordered join against an independent expected result. A separate workspace rebuilds each edition from scratch. Run it from the checkout with `uv run python tools/bench-manifest-refresh.py --items 128`. The first local sample used six concurrent trivial shell workers.

| Revision to a 128 item manifest | Selective worker calls | Fresh worker calls |
| --- | ---: | ---: |
| Initial edition | 128 | 128 |
| Identical input | 0 | 128 |
| Reverse order | 0 | 128 |
| Change one value, retain its ID | 1 | 128 |
| Insert one new ID | 1 | 129 |

The selective one-value comparison took 1.05 seconds against 1.45 seconds for a fresh build in this sample. Removing 127 worker calls saves much less than 127 times the elapsed time for trivial commands. Both invocations still start Python, load the workflow, read the manifest, and open a checkpoint. The test establishes how many dispatches can be avoided. With 512 items, one revision ran one worker in 1.05 seconds against 512 workers in 2.70 seconds. Both joins contained the current 512 values in order. Elapsed times are individual observations on this host. Actual time and API charges depend on the worker.

## Moving data between APIs and a database

Two clean local work directories each invoked a GitHub REST read through `gh api` and an anonymous Jira Cloud REST read through Python. Each adapter returned JSON containing a string ID and a display key. sqrlly validated the records against the same JSON Schema and passed their fields to a downstream command. That command opened a separate SQLite database and upserted the records using `(scope, id)` as its primary key. Both runs succeeded. The database held two rows after six nodes ran across the two workspaces.

| External read | Returned ID | Returned key |
| --- | --- | --- |
| GitHub issue in `christopherseaman/sqrlly` | `6539050029` | `56` |
| Jira Cloud project on `ecosystem.atlassian.net` | `14871` | `AA` |

The public reads can be repeated independently. Access and responses can change over time.

```bash
set -euo pipefail
gh api repos/christopherseaman/sqrlly/issues/56 --jq '{id, number}'
curl --fail --silent --show-error https://ecosystem.atlassian.net/rest/api/3/project/AA |
  jq '{id, key}'
```

One execution environment handled two different provider clients. The database enforced uniqueness even though the workspaces shared no checkpoint. The read adapters needed no new node kind. Real vendor writes, permissions to transition Jira issues, and Clarify imports have separate acceptance tests. [GitHub issues API](https://docs.github.com/en/rest/issues/issues), [Jira project API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-projects/), [Clarify matching rules](https://developer.clarify.ai/docs/guides/import-crm-data)

## A committed write with a lost acknowledgment

A sqrlly command committed a row to SQLite and then exited with status 7. After an acknowledgment became available, `--resume` reran the failed command. The first workflow invocation exited 1 and its recovery exited 0 in both trials.

| Sink contract | Committed rows after recovery |
| --- | ---: |
| No deduplication key | 2 |
| Same caller business key passed through `--var` and enforced by a unique constraint | 1 |

This small control matters for the second day. A new runner identifier earns its place only if it helps a case the caller's own key cannot already cover. Dispatch identity also cannot confer deduplication on an API that accepts two independent creates. The adapter must be able to query an existing result, use a conditional operation, or report that the outcome is unknown.

## An independent cloud handle and a changed local artifact

A sqrlly command queried existing GitHub Actions run `44991535037`. Another fresh workspace, given only the same remote run ID and repository scope, read the same completed status, successful conclusion and run attempt 1. The experiment used GitHub as the owner of run state. It exercised a remote lookup after replacing the local workspace. It did not launch a job, reattach sqrlly to a running cloud process, or test Claude cloud. [Cloud workflow run](https://github.com/christopherseaman/sqrlly/actions/runs/44991535037)

In a separate test a local command produced a declared output file. An external edit changed its contents after successful settlement. Bare resume exited 0 and the edited bytes stayed in place. This is consistent with recovery from an existing checkpoint. An independent consumer that needs evidence of the original bytes requires another check. Day three compares ordinary checksums with evidence attached to actual producing nodes and execution outcomes. [Program and next checkpoints](../engine-research-program.md)
