# November 22 checkpoint on operation identity

Issue #57, starting commit `b5b41b5`. Keep caller-supplied operation keys. A prototype keyed by the actual checkpoint run ID and node address matched the explicit key through recovery in one workspace. It created an extra effect when a fresh workflow invocation retried the same business operation. No engine API or retry behavior changes. [Research program](../engine-research-program.md) · [Baseline](2026-11-22-baseline.md) · [Transport](2026-11-22-transport.md)

## Procedure

The offline tests run the public CLI in separate processes. The CLI runs a Python adapter subprocess against a local SQLite sink outside the workflow workdir. The sink records calls and effects separately. In loss mode the transaction commits before the adapter exits nonzero without printing the success acknowledgment. Rejection mode records a call and exits nonzero before making the business change. The keyed sink atomically inserts on a unique operation key, checks that a repeated key has the original payload, and acknowledges the existing effect. The unkeyed control inserts with a null key. The candidate reads the private `sqrlly_runs` row in the single-workflow fixture and appends the node address. That lookup is experimental instrumentation. At rejection and acknowledgment loss the checkpoint had a failed node and no completion for it. The caller key survived as a run variable. Recovery retained the same thread, then recorded completion. Rerun-from retained the thread and dispatched again. A fresh invocation in the same workdir selected a new run ID. The explicit key was reused in the fifth call and advanced in the sixth. The candidate token was identical across the first four calls. Using a new token for every fresh run enabled a distinct sixth call at the cost of a duplicate fifth call.

With one configured command backend retry, two subprocess calls settled as one checkpointed node attempt. The first committed before exiting with a lost acknowledgment. The second made the effect count two without a key and kept it at one with the explicit key. This extends the baseline's two-versus-one result from process-level resume to retry within dispatch. ## Engine addresses and retry boundaries

- **Dispatch.** Templates render once per dispatch before the backend command retry loop. Explicit argv or environment keys stay the same through that loop. The command retry budget defaults to zero. A configured retry can reissue a nonzero command after it has committed. Output validation is a separate replay loop, and a route or eval that selects retry can execute a new node body. [Dispatch](../../../src/sqrlly/runtime/executor/dispatch.py) · [Output checks](../../../src/sqrlly/compile/outputs.py) · [Routing](../../../src/sqrlly/compile/nodes.py)
- **Foreman.** Git isolation has a run-scoped snapshot address with nested parent components and fan-out versioning. An isolated dispatch records a null sentinel before execution and replaces it with the result. An interrupted record can stop recovery, and an eligible retained successful record can avoid a redispatch. A recorded failure can be dispatched again. A retained output ref with missing completion can stop recovery. None of those local records establishes the fate of a remote commit. The measurements here ran outside Git. [Foreman](../../../src/sqrlly/runtime/foreman.py)
- **Fan-out and routing.** Stable child addresses track explicit item IDs. Input hashes and producing state distinguish changed values for refresh. A new back-route wave clears the reuse eligibility of its children and schedules them again. A child can also execute multiple bodies inside a single wave because of eval retry. Child address, input revision, wave, and attempt answer different engine questions. [Fan-out scheduling](../../../src/sqrlly/compile/graph.py) · [Worker loop](../../../src/sqrlly/compile/dynamic.py)
- **Subgraphs and checkpoints.** Each child invocation initializes fresh child state with rendered `workflow.with` bindings. Logs and Foreman qualify scope by the parent reference, while the parent checkpoint records the wrapper’s outcome. The latest-run pointer is scoped to workflow path, name and workdir. Resume reseeds the prior state and clears failures. The log invocation ID changes independently of that checkpoint run. Neither a log ID nor a child-local workflow name serves as a business key. [Subgraphs](../../../src/sqrlly/compile/subgraph.py) · [Checkpoint and run lookup](../../../src/sqrlly/cli/main.py)

## Counterexamples and contract

One node and two invocations suffice to refute the run-scoped candidate as a universal business key. The first call commits and loses the acknowledgment. A fresh invocation submits the same request for recovery. The run ID changes and the cooperating sink admits a second effect. The other direction fails too. Two identical requests from the same node can intentionally represent separate operations, so a key made stable across invocations by removing the run ID or hashing the payload can incorrectly merge them. Adding wave or attempt to every key can turn a replay into a new business write.

The narrow contract is caller-owned scope and intent, with sink-owned deduplication or reconciliation. The caller supplies a key for the destination, action and logical operation, keeps it on recovery, and advances it for deliberate new work. The cooperating sink enforces uniqueness with the effect and can return the recorded result. Carry the key through `--var`, item data, or `workflow.with` as appropriate. A caller that must recover in another workdir needs a durable source for the key.

An API that accepts unconditional creates and supports neither idempotency tokens nor a reliable scoped lookup has two indistinguishable outcomes after a lost reply. The request may have committed, or it may never have reached the service. Repeating it can duplicate an effect in the first case. Suppressing it can omit the effect in the second. A stable token kept only by the runner changes neither case. The adapter must surface an unknown outcome until it can reconcile, and the workflow must avoid replaying the mutation via backend, output-contract, eval, routing or resume paths while it is unresolved. Transport’s loopback control already observed two committed rows after a blind replay and a lookup that became ambiguous. [Transport counterexample](2026-11-22-transport.md)

No vendor writes, credentials, Git worktree execution, concurrent workflow invocations, abrupt process kill, or host failure were exercised here. The SQLite commit followed by a deliberate process exit represents loss of a success acknowledgment.
