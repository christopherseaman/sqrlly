# November 22 checkpoint on nested Git recovery

Issue #59, starting revision `d128d75`. A repeated workflow can lose its child graph state after an isolated command has promoted a file and cleaned up its worktree. The parent knows the item failed, and Git knows what file revision settled. The command's stdout and structured JSON null were only available to the discarded child state and dispatch record. The baseline refused to run the isolated command again. ## Recovery boundary

The candidate records the validated command result and output-validation attempt count before snapshot settlement. A process interruption during the write leaves either the previous file or the complete new file at the receipt path. Reuse of a validated result requires a versioned receipt with a matching checksum, the current run and full Foreman address, a matching invocation input digest, and matching Git input and output commit IDs. When the output commit matches the Git settlement marker, recovery reconstructs the successful node update and skips execution, file validation against the removed worktree, and promotion. A receipt recording a promotion conflict can instead reuse the validated result before a marker exists. The engine checks that the retained owned tree matches its output snapshot, consumes the recorded conflict, and retries promotion. A clean fresh run prunes the previous inactive run's receipts and snapshots from the Git common directory.

Durable receipts are limited to a top-level repeated workflow reference with a child dependency DAG. The reference has no eval, route, or output contract. The child DAG has no eval, route, repetition, or further workflow references. Within those bounds, an isolated `run` leaf has one validated body result per item generation. The generation lives in the Foreman scope. The digest covers the item value, the leaf's template binding graph including shared objects and structured output text, its node definition, effective settings, and loaded output schema. Explicit refresh after an item changes advances the generation. An intentionally rerun completed wrapper also uses a new generation.

The first invocation can also recover a promoted ordinary isolated command from its retained worktree when the wrapper declares outputs or the child DAG contains evals without explicit routes. An implicit eval retry reenters only the evaluated node, which is ineligible for result recovery. The validated receipt lives beside the raw dispatch in Git's worktree administration directory. It binds the initial invocation identity and exact validated result, including the attempt count, to the raw dispatch digest, input revision and settled output revision. Recovery checks ownership and the retained tree before idempotent settlement finishes cleanup. Each declared file pattern must still match, and every current match must be a regular file covered by the Git snapshot. Worktree removal closes this path. Missing or mismatched evidence preserves the guard.

For `promote: false`, an interrupted dispatch can reenter the existing cache and output-validation path while the owned worktree remains. After output capture, Foreman publishes checksummed evidence binding the raw dispatch bytes to the scoped input ref, input commit, invocation digest, and captured output commit. Resume requires that evidence, the raw success record, and a retained tree whose Git-normalized content and HEAD match the identified output snapshot. Output validation and normal cleanup then run. The evidence disappears with the worktree. An interrupted dispatch without the binding or without the retained worktree remains guarded.

A nested LangGraph checkpointer could preserve the whole continuation, including completed ordinary nodes, branch decisions, measurements and retry history. This compiler currently invokes a newly initialized child graph through a wrapper, including inside a fan worker, and the CLI reseeds the outer checkpoint on resume. A child checkpointer would need a stable namespace for each wrapper invocation and wave, a continuation policy across outer reseeds, and a defined order between checkpoint, promotion and cleanup. A checkpoint written after promotion still leaves a window for a missing acknowledgment. A checkpoint written before promotion still needs proof that the external settlement completed. The receipt uses the existing Git settlement marker to close the process-level acknowledgment window for one validated body result and leaves continuation semantics outside this experiment.

| Loss immediately before promotion | The validated receipt exists and its worktree is retained. The artifact is absent. Without a settlement marker, resume stops, the counts stay at one each and there is no join. |
| Loss immediately after the command exited | The real effect was recorded once, Git's dispatch record is `null`, the artifact was never promoted and resume leaves the counter and join unchanged. |
| Missing, legacy raw result, truncated, foreign scope or wrong output commit | The already promoted file stays in place. Resume reports missing completion, makes zero additional calls and emits no join. Wrong scope and output tests recompute the checksum to exercise identity checks independently. |
| Changed value under the same ID | Bare resume rejects the old result and keeps the file at `1`. Explicit refresh promotes `3`, adds exactly one `b:3` call, preserves one call for each original value and emits `["b:3:null", "a:2:{\"value\":\"2\"}"]` in manifest order. |
| Nested route retry | Each item executed its isolated node twice. Git retained two output refs total, one per item. The scope therefore collapsed two attempts into one address even though there were four real effects. No receipts were written. Resume guards the prior promotion and leaves the four effects intact. |
| Clean fresh run after failure | The new run executes both items intentionally. Its two receipts remain, the earlier receipt directory disappears and the join has the original expected order. |

The injected loss cases raise at the named boundaries in the real executor path. They exercise process-visible state while preserving Git and the real shell commands. They do not simulate power loss, concurrent metadata tampering, external service acknowledgment, or abrupt host termination.

Recovery requires the parent checkpoint to identify the active item generation. The receipt binds Git revisions and declared invocation data. It does not certify that the base still contains those bytes, that a script's external dependencies stayed unchanged, or that an external effect happened exactly once. A pending promotion without a settlement marker or a recorded conflict remains guarded. The guard also applies to prior promotions from explicitly routed or deeper child graphs and to promotion of an evaluated node itself. If interruption occurs after promotion but before tree removal, durable receipt recovery can reuse the result while the leftover tree remains available for inspection. The receipt protocol assumes trusted local Git metadata and does not promise power-loss durability.

A matching output-rejection receipt, retained dispatch record, and unchanged output snapshot allow resume to revalidate the rejected output, including for an isolated leaf with `promote: false`. If validation still fails, the existing output retry policy can dispatch again. The promoting test exhausts validation with three calls for `b`, then observes a fourth call on resume before promotion. A changed raw dispatch record or retained snapshot blocks recovery at three calls. An interruption after consuming the rejection receipt and making the fourth call blocks a further retry without new evidence.
