Reapplied the snapshot lease extraction at its three current call sites, keeping #59's receipt and snapshot logic. The CLI acquires a SQLite write transaction on a per-thread lease file before publishing a new run ID or reseeding a resumed checkpoint. It holds that transaction through executor and checkpoint connection cleanup. The existing CLI error translation reports `This workflow run is already active`.

The resume regression starts with a failed invocation and drives four competing modes against the held run. Each contender must exit 1 with the run-active message and leave the effect table unchanged. In the normal case the holder exits 0 and the next resume skips the completed write. In the SIGINT case the holder exits 130 before the write, then a new resume exits 0 and commits one row. In the independence case, a second fresh invocation finishes and commits its own row while the first fresh invocation is still running. After clean exit, the tests require one stable lease file per run and no residual journal. A local sample had zero-byte, zero-data-block lease files after release. An active transaction could have a 512-byte journal. The files deliberately retain their inode identity. They consume directory entries and inodes linearly with fresh runs. No long-running accumulation benchmark is needed for this fix, and concurrent pruning would need a separate protocol.

These guarantees apply to cooperating launchers using the same store and lease files on a filesystem with working SQLite locks. Checkpoint copies can be opened independently. A fresh invocation selects a new run and can repeat effects. The Git concurrency control retained separate `first` and `second` output snapshots while both runs overlapped. A third clean run pruned the earlier inactive snapshots and retained only `third`. A hard kill can leave an external command active, and deletion and replacement during reseeding still leave a crash window. A run lease addresses the observed runner collision. It cannot recover an acknowledgment from the sink.

## Checkpoint ordering at a repeated fan-out boundary

The existing Git wave test stops the real launcher after child `a` has started in wave three, with earlier promoted results `a,b`. On archived `08fd1db`, both modes recovered with exit 0 in one diagnostic run and the base `round` advanced to 4. With the lease alone, bare resume exited 0 and refresh exited 1 with a manifest-drift error in one rerun. Neither result reliably reached the interrupted-dispatch guard. The strengthened test reads SQLite after SIGTERM and before recovery. Archived `08fd1db` had persisted `work` attempt 1 in both cases, even though wave three had already started.

The owning layer is the runner's LangGraph stream. The installed LangGraph 1.2.22 default permits saving one step while the next dispatches. The runner now selects synchronous durability when a checkpointer exists, so the previous outer step is written before the next starts. The installed LangGraph implementation requires a checkpointer for that barrier. The runner leaves its default mode in place for uncheckpointed graphs, including dry runs. Each strengthened test asserts persisted attempt 3, manifest `["work::a"]`, `fan_ready=false` and no completion for `work::a`. Both resume modes then exit 1 with `Interrupted dispatch`, leave the base results at `a,b`, and retain the tree with `a,b,a`. This adds a checkpoint write barrier between steps. Dispatch acceptance and its result still span separate systems, and the resume reseed window remains.

## Inputs for portable evidence (#58)

Carry forward the workflow edition or content digest, logical item identity and producing input revision, encoded node address and attempt/invocation provenance, and whether evidence came from execution, checkpoint reuse or Git settlement. Keep the external operation key and opaque handle with the scope in which each is meaningful. Record acceptance, observed completion, and successful collection as separate events. Include a digest of the bytes and the artifact reference, plus how to resolve that reference after the worker is gone. An independent verifier should test moved, changed and inaccessible bytes separately, distinguish a missing handle from an unavailable store, and query the external owner where verification depends on its state. A copied checkpoint or successful resume is insufficient evidence of file integrity. Git receipts can establish local settlement when their evidence is available. They cannot prove an external commit.
